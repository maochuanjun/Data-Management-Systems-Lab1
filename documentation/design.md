# MongoDB 数据库设计与关键逻辑

本系统用于管理问卷、可复用题目、版本和填写记录。业务数据全部保存于 MongoDB，后端使用 Go。本文集中说明集合划分、文档结构、索引、约束及主要数据操作。

## 1. 为什么这样设计

用户、登录会话、问卷定义和填写记录分别放在 `users`、`sessions`、`surveys`、`responses` 中。可复用题目的归属与共享、不可变版本、个人题库则分别放在 `question_templates`、`question_versions`、`question_banks` 中。集合边界对应不同的访问方式和生命周期。

| 集合 | 关键字段 | 用途 |
| --- | --- | --- |
| `users` | `_id`, `username`, `passwordHash`, `createdAt` | 用户信息，密码以 bcrypt 哈希保存 |
| `sessions` | `_id`, `userId`, `expiresAt` | 登录会话，令牌哈希作为文档 ID |
| `surveys` | `_id`, `ownerId`, `title`, `status`, `questions`, `deadline`, `revision` | 问卷及题目配置 |
| `responses` | `_id`, `surveyId`, `answers`, `path`, `submittedAt` | 每次提交的答卷 |
| `question_templates` | `_id`, `ownerId`, `sharedWith`, `sharingRevision`, `nextVersion`, `ready` | 题目归属、共享授权与版本分配 |
| `question_versions` | `_id`, `questionId`, `version`, `parentVersionId`, `restoredFromVersionId`, `question` | 不可变题目内容与版本来源 |
| `question_banks` | `_id`, `ownerId`, `name`, `versionIds`, `revision` | 个人题库及显式固定的版本 |

**题目嵌入问卷。** 创建、编辑和填写问卷时，一般要同时取出题目、选项、限制条件和跳转规则，所以把它们放在 `surveys.questions` 数组中，一次读取即可取得整份问卷配置。独立题目在草稿中由创建者编辑；引用题目固定版本内容，跳转规则仍由当前问卷管理。发布后不再允许修改题目。程序还设置了最多 100 道题的限制，以控制单份问卷文档大小。

**答卷独立存储。** 一份问卷可能产生大量提交。如果把所有答卷都放进 `surveys`，同一文档会持续增大，多人填写时还会集中更新这个文档。因此每次提交向 `responses` 插入独立记录，再通过 `surveyId` 关联问卷。这样既便于多人提交，也便于按问卷统计。

**用户与会话分开。** 用户账号长期存在，而会话有过期时间；拆分后可通过 TTL 索引清理过期会话，不必更新用户文档。账号与问卷、答卷之间使用 ID 引用。

## 2. 为什么不用关系数据库式结构

如果按关系模型设计，通常会把问卷、题目、选项、跳转规则及提交答案分别拆表，用主键、外键和 JOIN 还原整份问卷。这种方式有成熟的完整性约束，在复杂关联查询中也有优势；并不是关系数据库无法实现问卷系统。

但对于本项目，最常见的操作是**按 ID 读取一份完整问卷**。题目、选项和规则通常一起使用，若按多张关系表拆分，会增加关联查询及对象组装工作。MongoDB 的嵌入文档能够更直接地表示这组整体使用的数据。另一方面，答卷需要独立存放、不断增加，因此没有把所有数据塞进同一集合或同一个大文档。

这种设计的代价是：题目数组适合整卷读写，不适合无限增长；MongoDB 不会自动维护 `ownerId`、`surveyId` 等字段的外键关系，关联合法性要由程序负责。因此这里选择的是**按访问方式决定嵌入或引用**，而不是把关系数据库简单替换成 MongoDB。

## 3. 为什么适合 MongoDB

本项目使用 MongoDB 的原因主要与数据形态和访问方式有关：

1. **嵌入式文档。** 一份问卷包含不同题型、选项、校验条件和跳转规则，BSON 文档能把这组层次化数据放在一起。
2. **不同题型的答案。** 单选保存一个选项 ID，多选保存 ID 数组，文本保存字符串，数字保存数值。答卷的 `answers` 对象可以按题目 ID 保存不同类型的值。
3. **按问卷聚合。** 统计查询以 `surveyId` 为筛选条件，使用 MongoDB 的 `$match`、`$facet`、`$group`、`$sum` 和 `$avg` 计算结果。
4. **索引和文档校验。** 使用唯一索引、TTL 索引及 JSON Schema 约束基础结构，业务规则由 Go 再校验。

这些优点也有边界：跨集合的强引用完整性需要应用层维护；若未来要进行大量跨问卷、多维关联分析，可能要调整数据模型或统计方式。

## 4. 题目和答卷结构

当前前端按单选、多选、填空三种业务题型提供编辑入口；填空包含文本和数字两个子类型：

| 题型 | 数据表示 | 限制 |
| --- | --- | --- |
| 单选 | `type: "single"` | 有效选项、是否必答 |
| 多选 | `type: "multiple"` | 有效选项、最少和最多选择数量；两者都设为 2 时要求恰好选择两个不同选项 |
| 填空 | `type: "fill"`，`fillType: "text"` 或 `"number"` | 文本长度；数字上下限和整数要求 |

问卷中的一条题目配置示例（仅展示相关字段，不是可直接插入的完整问卷）：

~~~json
{
  "id": "q1",
  "title": "是否继续填写？",
  "type": "single",
  "required": true,
  "options": [
    {"id": "yes", "label": "是"},
    {"id": "no", "label": "否"}
  ],
  "validation": {"integer": false},
  "rules": [
    {"operator": "eq", "value": "no", "target": "END"}
  ]
}
~~~

每条规则包含判断操作符 `operator`、比较值 `value` 和跳转目标 `target`。目标为后续题目的 ID 或 `END`。

一份简化的答卷示例：

~~~json
{
  "_id": "response_001",
  "surveyId": "survey_001",
  "anonymous": true,
  "answers": {"q1": "yes", "q2": 21},
  "path": ["q1", "q2"]
}
~~~

实际存储还包含 `schemaVersion` 和 BSON Date 类型的 `submittedAt` 等字段。这里的 `answers` 按题目 ID 存储；`path` 是服务端根据规则计算的实际作答顺序，而不是浏览器指定的可信结果。

历史测试样例中，填空题曾使用 `type: "text"`、`type: "number"`。当前前端新建或编辑时统一使用 `fill + fillType`；服务端为兼容旧数据和旧调用方式，仍接受 `text/number` 的读取及新写入请求，没有对所有 API 写入强制转换。可复用题目的新版本统一规范为 `fill + fillType`，原问卷 API 继续兼容历史编码。

## 5. 索引与数据约束

数据库创建和索引初始化位于 `internal/store/mongo.go` 的 `Init()`；MongoDB JSON Schema 位于 `collectionSchemas()`。

| 集合 | 索引 | 作用 |
| --- | --- | --- |
| `users` | `username` 唯一 | 不允许重复用户名 |
| `sessions` | `expiresAt` TTL | 过期会话清理 |
| `surveys` | `ownerId, createdAt` | 查询并排序某用户创建的问卷 |
| `responses` | `surveyId, submittedAt, _id` | 按问卷检索、稳定分页 |
| `responses` | `surveyId, dedupeKey` 部分唯一 | 禁止重复填写时进行数据库级去重 |

JSON Schema 检查基本字段是否存在、BSON 类型及部分枚举值。例如问卷状态仅允许 `draft`、`published`、`closed`；题型字段接受新表示和历史兼容表示。

MongoDB Schema **不能代替业务规则**：选项 ID 是否重复、跳转目标是否在后续题目、多选数量限制是否合理等，由 `internal/domain/logic.go` 中的 `ValidateSurvey()` 和 `ValidateAnswer()` 检查。对于禁止重复提交的问卷，后端根据问卷和账号生成 `dedupeKey`，并通过唯一索引防止两个并发请求重复插入。

**旧答卷去重兼容。** `Init()` 创建部分唯一索引后调用 `backfillLegacyDedupeKeys()`，为 `allowRepeat=false` 问卷中具有明确 `userId` 的历史填写账号恢复去重标记，使同一账号不能因旧记录缺少 `dedupeKey` 而再次提交。已有带键记录继续承担去重作用；没有有效标记时，按 `submittedAt`、`_id` 顺序为该账号最早的旧记录补键。如果已经存在多份历史重复答卷，只需一份记录持有唯一标记，其余记录连同原答案、路径、身份和提交时间均保留。

回填仅更新缺少标记的记录，重复初始化可以安全执行；并发初始化由唯一索引协调。遇到唯一键冲突时，程序先确认该问卷和账号对应的标记确实存在，再保留额外历史记录继续处理。对于既没有 `userId`、也没有去重标记的历史匿名答卷，系统无法可靠恢复账号，不会推测或补造身份关联。回归步骤见 [测试用例与结果](testing.md)。

## 6. 主要数据操作

**创建与发布。** 注册用户创建 `draft` 问卷；草稿更新使用 `revision` 作为乐观锁，防止旧版本覆盖新内容。发布时再次检查题目配置、截止时间及问卷是否为空。

**条件跳转。** `NextQuestion()` 按规则顺序查找第一条命中条件；没有命中就进入下一题。规则只允许跳向后面的题目或 `END`，不允许循环。最终提交时，`ValidateSubmission()` 从第一题重新计算路径，检查经过的每道题并拒绝携带被跳过题目的答案。

**保存与匿名。** 填写者必须登录。只有问卷设置 `allowAnonymous=true` 且本次提交选择 `anonymous=true` 时，答卷才不写 `userId`；未选择匿名时仍保存用户 ID。禁止重复填写时，匿名与实名提交都根据账号和问卷生成 `dedupeKey`，因此匿名不能理解为数据库层面完全不可关联。

**请求容量与业务长度。** 答卷提交接口的 JSON 请求体上限为 16 MiB，其他 JSON 接口为 1 MiB，超限返回 413。请求体按字节计量；文本的 10,000 上限按 Unicode 码点计量，问卷最多 100 道题。非 BMP 字符在 JSON 中可以用两个 `\uXXXX` 转义单元表示，一个字符占 12 个请求体字节，因此不能用单个文本字段的字符数直接估算整卷请求大小。16 MiB 的答卷容量覆盖这些业务上限组合下的正常紧凑 JSON 编码；题目上的 minLength/maxLength 等约束仍独立生效。

**统计。** `Stats()` 先按 `surveyId` 筛选记录，再对单选、多选计算选项次数，对数字填空计算平均值。原始文本和数字填写内容由 `answerValues()` 按页读取，避免把所有长文本放进一份聚合结果。统计计数对应**提交记录数**，允许重复提交时不能视作去重人数。

`answered` 的精确定义是该题答案字段存在且不为 `null` 的记录数。允许提交的空文本和空选项数组仍计入 `answered`，但空数组不增加任一选项的选择次数；数字 0 计入回答数及平均值。题目被跳过、答案缺失或为 `null` 时不计入。

## 7. 可复用题目、版本与问卷快照

单纯将题目嵌入问卷不能表达跨问卷的共同来源；直接让问卷读取一份可变题目，又会使题目修改改变已经发布的问卷。因此这里保留问卷嵌入内容，同时增加独立题目和不可变版本：

~~~text
question_templates（归属、共享）
  └─ question_versions（内容、父版本、恢复来源）
       ├─ question_banks.versionIds（显式固定）
       └─ surveys.questions（内容快照 + 来源题目/版本 ID）
            └─ responses.answers[问卷内局部题目 ID]
~~~

题目 ID 标识一个版本族，版本 ID 标识某一份不可变内容，问卷局部题目 ID 标识该题在一份问卷中的某次出现。这三个 ID 承担不同职责。一个版本可以被多份问卷引用，也可以在同一问卷中出现多次；选项 ID 保持原版本值，答卷键则继续使用局部题目 ID。

`question_versions.question` 保存标题、题型、必答、选项和校验约束。跳转规则引用问卷中的其他题目，因而只保存于问卷快照的 `rules`。服务端检查新引用的来源版本和内容一致，前端锁定引用内容；需要修改时创建新版本，或将该实例转换为独立题目。独立题目移除来源后不再参与原题目的跨问卷统计。

每次修改产生新版本，`parentVersionId` 指向用户选择的基线；用户可从任意历史版本派生，多个分支同时存在。恢复也插入新文档：内容复制历史目标，父版本指向恢复时读取的最新版本，`restoredFromVersionId` 记录恢复来源。版本号用于展示和唯一编号，父版本关系决定分支，旧版本不会被修改。

题库保存版本 ID 列表而非“最新题目”引用。更新题库固定项需要显式选择，且只更新该题库；已经保存的问卷不会跟随更新。题库使用 `revision` 条件更新/删除，避免旧页面覆盖新修改。删除题库不删除题目版本。

### 共享与权限边界

共享名单保存在题目级别，由作者按用户名管理。被共享用户可读取所有版本并引用到自己的问卷，不能修改作者的题目或共享名单。版本历史、使用情况和统计接口都先检查题目读取权限。

共享名单使用独立的 `sharingRevision` 做条件更新，并在同一原子操作中递增，避免旧页面恢复另一页面刚撤销的权限。历史文档缺少该字段时按 0 匹配，首次更新使用 `$inc` 写入 1，无需批量迁移。内容版本的创建和恢复不改变共享版本号。

题目详情页的版本保存、恢复和共享保存使用同一个忙碌状态；请求期间禁用详情页表单及操作按钮，失败后保留输入并恢复编辑。共享成功后使用服务端返回的名单和版本号，冲突不会自动重试。离开页面后，旧请求的响应不能刷新新页面或显示过期提示。

详情页内会替换编辑器或重载详情的操作还会检查未保存内容。恢复历史版本前检查题目草稿和共享名单；切换编辑版本、取消编辑前检查题目草稿；保存新版本前检查尚未提交的共享名单。存在修改时先确认，选择取消便保留输入且不发送写请求。题目标题、选项、约束和版本说明均参与草稿比较；改回原值不再提示，约束对象的键顺序不影响比较。保存共享仅更新名单和共享修订号，保留题目草稿。

新增题目、创建题库、保存或删除题库，以及跨问卷统计也需要保护异步响应。用户离开发起操作的页面后，旧请求即使成功或失败，也不能再次跳转到旧对象详情或覆盖当前通知；统计切换版本后，先前查询的错误同样不能盖过新结果。本次修订为这些回调增加页面有效性或当前查询检查。已经发出的写请求仍可能在服务端完成，界面丢弃过期响应不表示撤销了数据库操作；返回相应列表时应以服务端实际保存的结果为准。

撤销共享阻止后续读取和新增引用，但原问卷嵌入快照仍可填写、保存、发布和查询单卷统计；题目的跨问卷统计接口仍要求当前题目读取权限。保存草稿时，仅当局部 ID、来源及内容与数据库中的原快照一致，才允许保留已撤销授权的引用；本地跳转规则仍可编辑。题库也允许保留原固定项，保留 ID 不授予新引用权限。

使用情况向用户展示其自己创建的问卷明细。题目作者还可看到全局引用问卷数及实例数，用于判断修改影响；其他用户问卷的名称、ID 和答案不返回。跨问卷统计始终以当前用户的 `ownerId` 筛选问卷，不因为共享题目而扩大答卷访问权限。

### 新索引与创建恢复

新集合的 Schema 和索引位于 `internal/store/library.go` 的 `initLibrary()`，由原 `Init()` 接续执行。

| 集合 | 索引 | 用途 |
| --- | --- | --- |
| `question_templates` | `ownerId, ready, createdAt`；`sharedWith, ready` | 本人题目和获共享题目 |
| `question_versions` | `questionId, version` 唯一 | 版本顺序及并发唯一性 |
| `question_banks` | `ownerId, createdAt` | 个人题库列表 |
| `surveys` | `ownerId, questions.sourceQuestionId` | 本人的题目引用及统计入口 |
| `surveys` | `questions.sourceQuestionId, questions.sourceVersionId` | 题目和版本引用查询 |

单机 MongoDB 下，创建题目族与 v1 涉及两个文档。系统先写 `ready=false` 的题目族，再写 v1，最后标记 `ready=true`；查询只显示已就绪题目。若写入响应不确定，不删除可能已经成功写入的数据。后续 `Init()` 只将确实存在 v1 的待就绪题目恢复为可见；缺少 v1 的记录继续隐藏。

新增版本通过原子 `$inc` 分配编号，唯一索引阻止重复版本号；插入失败可能留下编号空缺，因此“最新版本”查询实际存在的最高版本文档，不把计数器误当作版本存在的证据。题目内容没有原地更新接口；该不可变约束由应用写入路径维护，数据库管理员直接修改集合不在该约束范围内。

## 8. 跨问卷统计与兼容

统计从当前用户拥有的问卷开始筛选，再展开有相同来源的题目，通过 `surveyId` 关联答卷，使用局部题目 ID 取出答案。`$lookup` 后紧接 `$unwind`，避免先物化所有答卷的大数组。按版本分别执行选项计数、回答数、数字平均值及分布，防止选项含义或题型变更后混算。

数字分布使用 `$bucketAuto`，最多 10 桶；平均值直接来自全部数值回答，而非各问卷平均值的简单平均。回答数以题目实例为单位，同一版本在同一份答卷中出现两次便计两次。统计的问卷数只包含有实际回答的问卷，与使用情况中统计全部现存引用的问卷数有所区别。

例如，本人问卷 A 提交一个数值 100，本人问卷 B 在每份答卷中两次引用同一版本，三份答卷依次为 10/11、20/21、30/31。结果有 7 个题目实例、2 份贡献回答的问卷，平均值为 `223/7`。另一用户问卷中的 999 只属于该用户的统计。这个例子同时检验跨问卷汇总、重复出现和用户权限，具体断言见 [测试说明](testing.md)。

全部版本视图仅返回摘要。选择具体版本后，原始答案按稳定排序取 `limit+1` 条判断下一页，对外每页最多 50 条，避免一次返回全部长文本。该查询使用动态字段表达式形式的 `$getField`；运行环境以 MongoDB 8.0 为基准，相关表达式从 7.2 起可用。操作符定义见 MongoDB 官方文档：[$getField](https://www.mongodb.com/docs/manual/reference/operator/aggregation/getfield/) 与 [$bucketAuto](https://www.mongodb.com/docs/manual/reference/operator/aggregation/bucketauto/)。

升级以增量集合和可选来源字段为主。已有 `surveys`、`responses` 的内容和局部题目 ID 继续有效；没有来源的旧题目不按标题猜测同一性，也不重写历史答卷。将旧问卷题目另存为可复用题目会创建新实体，历史独立题目不会自动归入新题目的统计。原来的历史去重回填、题型兼容、归档/重开、16 MiB 答卷请求容量继续执行。

当前关闭操作与已经进入处理的并发提交并非单一事务边界；统计摘要和原始答案多次查询也不保证同一时点快照。题目列表和版本历史尚未分页，大量版本会增加读取及逐版本统计成本。若数据规模扩大，可沿现有仓储接口增加列表游标和统计缓存；仍应保留不可变版本、显式固定和用户数据权限这些业务约束。
