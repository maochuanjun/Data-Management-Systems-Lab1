# AI 使用日志

本项目使用 ChatGPT 和 Codex 辅助需求分析、Go 与 MongoDB 实现、前端交互、测试和文档整理。我提出技术路线、使用反馈和课程要求，结合 AI 的方案说明继续修改、验证和整理。以下记录覆盖两个阶段，按任务说明提示词、产物、后续修改及个人工作。

## 一、工具与协作方式

ChatGPT 用于讨论需求、数据结构和设计理由，也参与代码审查和报告修改；Codex 用于在项目中实现、运行测试和定位问题。AI 参与了实际代码的生成、重构与缺陷修复，主要涉及 `internal/domain`、`internal/store`、`internal/web` 和 `tests/`。

协作方式是先明确功能和约束，再形成可运行版本；根据运行结果和个人使用反馈修改；最后对照需求、实现位置、测试输入与断言检查结论。第二阶段沿用第一阶段的 Go 分层、问卷快照和答卷结构，在原模块中增加题目、版本和题库能力。

## 三、AI 辅助产物中的问题与修正

| 问题与检查理由 | 修改方式 | 代码与验证位置 |
| --- | --- | --- |
| 题型术语和跳转条件容易把显示文字与内部 ID 混淆。 | 编辑器显示单选、多选、填空及填空子类型；选择可读选项配置规则，保存稳定 ID；兼容历史表示。 | `internal/domain/logic.go`、`internal/web/static/app.js`，领域与前端测试。 |
| 匿名曾表述为免登录或完全不可关联，缺少必要条件。 | 明确必须登录，问卷允许匿名且本次选择匿名时才省略新答卷的 `userId`；禁止重复时仍保存账号级去重键。 | `internal/web/server.go`、`tests/integration/http_test.go`。 |
| 只有部分唯一索引无法恢复缺少防重键的历史账号限制。 | 初始化时为能确定身份且需要防重的旧记录补键；保留已有键及所有旧答卷，不推测无法识别的匿名账号。 | `internal/store/mongo.go`、`compatibility_test.go`、`legacy_dedupe_test.go`。 |
| 逐题合法的长文本答卷可能超过原统一 1 MiB 请求上限。 | 最终答卷接口改为 16 MiB，其他 JSON 接口保持 1 MiB；超限 413，格式错误 400，入库后读回完整答案。 | `request_size_test.go`、`response_size_test.go`。 |
| 统计说明容易混淆提交份数、引用次数、回答实例与人数；不同问卷样本量也不相同。 | 明确空值和 0 的口径；按实际回答计算平均值，按具体版本隔离；用 100、10/11、20/21、30/31 验证 `223/7`，排除他人的 999。 | `mongo_test.go`、`TestLibraryUsagePrivacyAndWeightedNumericStats`。 |
| 新题目涉及多文档写入，版本计数已推进不表示版本文档一定存在。 | 使用就绪标记隐藏未完成创建，只恢复已有 v1 的对象；读取最新实际版本，允许分配失败后的编号空缺。 | `internal/store/library.go`，创建中断恢复与版本空号集成测试。 |
| 两个旧页面保存共享名单可能覆盖新撤销的权限。 | 引入独立 `sharingRevision`，原子条件更新；冲突返回 409，不自动重发旧名单；页面写操作互斥。 | `sharing_test.go`、`library_concurrency.test.cjs`。 |
| 编辑、恢复和迟到响应可能丢失草稿或改变新页面。 | 草稿比较与离开确认、保存基准更新、请求期间锁定输入；按路由或查询代次忽略过期响应，首页创建也遵守同一规则。 | `frontend.test.cjs`、`library_concurrency.test.cjs`、`feedback.test.cjs`。 |
| 新增重复标签约束若无差别套用，会阻断旧已发布问卷或破坏历史恢复。 | 新配置严格检查标签；旧快照填写仍按原 ID，恢复忠实复制原文。恢复内容用于新问卷前需先修正。 | `tests/unit/feedback_test.go`、`tests/integration/feedback_test.go`。 |
| 按修复轮次不断追加说明，使第二阶段像补充记录，测试数字也容易沿用旧值。 | 按完整系统重新组织设计、接口、测试与报告，将阶段差异放到相应主题；分别记录最近完整回归与最新前端复跑。 | 本文、`testing.md` 和完整项目报告。 |

这些调整说明，AI 生成的代码和说明需要结合真实调用路径核对。数据库索引不能自动补齐旧记录，新校验不能随意改变历史内容，界面回调也不能只考虑请求发起时的页面。修复后仍需执行对应测试，而不是仅根据文字解释认定问题已经解决。

## 四、个人承担的工作与设计判断

个人工作主要包括以下方面。

1. **确定技术路线和学习目标。** 我提出使用 Go，希望先完成可运行版本再逐项理解；MongoDB 是课程约束，具体集合、接口和代码由 AI 协助实现。
2. **确定增量扩展方向。** 我要求在第一阶段基础上继续修改，保留主要功能和旧数据。第二阶段继续使用问卷内快照和独立答卷，新增题目、版本、题库集合；具体方案形成和并发处理有 AI 参与。
3. **作出权限与使用方式选择。** 我明确跨问卷统计只包含本人创建的问卷，并根据实际使用提出题型术语、规则配置、回退输入和未保存提醒等问题。
4. **修改仓库与报告。** 我持续调整、提交已有材料，删去不需要的说明，要求最终报告沿用第一阶段风格，并完整解释从原设计到新需求的变化。AI 按最新仓库内容继续整理。
5. **参与验证并核对结论。** 第一阶段我在本地运行过 Go 单元、前端、MongoDB 集成、静态检查、构建和 Chromium E2E。第二阶段的代码修正、自动化测试和独立复核有 AI 协助，具体执行范围按测试记录区分。我依据课程要求、实现位置和测试断言验收结果。

报告需要回答的八个问题分别落实为：原有四集合与分层是什么；复用、共享和历史要求为何超出原设计；为什么保留问卷快照并增加独立版本；哪些模块及接口扩展；来源字段和三个新集合如何表达关系；保存、恢复、共享与统计程序如何调整；旧题型、去重键、来源缺失和历史标签如何兼容；如何通过旧数据与原有流程回归确认旧功能可用。
