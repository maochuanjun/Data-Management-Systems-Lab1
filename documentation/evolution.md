# 第二阶段扩展约定

在当前可运行、可回归的系统上增量演进。新需求尚未发布，不预先猜测未知的业务模块。

## 已落实的边界

| 边界 | 当前实现 | 后续约束 |
| --- | --- | --- |
| HTTP 与业务 | Web 处理编解码、认证、权限；Domain 处理校验和跳转 | 新规则先定义领域行为及测试，再接接口和页面 |
| 持久化 | Web 的 Repository 接口注入 MongoDB Store | 保留业务与 API 验收，生产数据继续使用 MongoDB |
| 引用 | 稳定题目和选项 ID，规则保存为数据 | 不用题号或显示文字替代 ID，不误关联旧答案 |
| 结构版本 | 问卷、答卷的 schemaVersion | 明确新字段默认值、旧数据读取或迁移方式 |
| 并发编辑 | revision 乐观锁 | 编辑修订号不等于结构版本或发布版本 |
| 已发布内容 | 冻结题目和配置 | 如需编辑发布内容，增加发布版本及答卷引用，保留原版本 |
| 统计 | 有界汇总和独立稳定分页 | 不把无限增长的原始答案重新压进单个聚合文档 |
| 回归基线 | 固定版本 1 数据、公开 API、真实浏览器测试 | 不删除旧用例换取通过，明确需求变更才调整旧预期 |

这些边界已有代码与测试支持，没有引入微服务或插件平台。

## 每次迭代

1. 记录新需求、受影响的旧行为和兼容性要求。
2. 在 `tests/` 增加能够复现新需求或问题的失败用例。
3. 修改对应层；新增可选字段给出兼容默认值，不兼容时设计版本化读取及显式迁移。
4. 迁移限定数据库和版本，可重复执行，并验证旧数据未损坏。当前没有自动结构迁移工具，版本字段本身不代表已完成迁移。
5. 执行 `make integration` 和 `make e2e`，特别是固定旧数据兼容用例。
6. 更新 API、数据库设计、AI 记录和变更说明，保留独立 Git 提交及新版本基线。

## 兼容验收

`tests/integration/compatibility_test.go` 读取 `tests/fixtures/v1` 的固定 Extended JSON，而非用当前结构体生成旧数据。它验证历史用户、草稿、已发布问卷、答卷可读，初始化可重复，旧问卷可继续填写和统计，新旧回答共同统计，原答卷完整保留。

当前语义包括只向前跳转、首条匹配优先、登录后可匿名、按账号去重、按提交份数统计和发布后冻结。第二阶段改变这些语义时，应说明理由和旧数据的处理方式。
